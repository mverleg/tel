# Macros

This chapter covers Tel's stance on metaprogramming: macros, reflection,
`derive` declarations and attributes, and compile-time evaluation. The short
version is
that Tel does **less** metaprogramming than most languages, on purpose. This
page explains the macro position; the others cover the narrow features that do
earn their place.

## Tel pushes toward less metaprogramming

Embedded scripting favours *less* metaprogramming, not more. The reasoning runs
straight from the [priorities](../02-philosophy/01-priorities.md):

- **Stability.** Tel is frozen at 1.0 and has many host implementations
  maintained by other people. A powerful macro system is a large, open-ended
  surface that every implementation must reproduce identically. Less
  metaprogramming means less that can drift between hosts.
- **Fast, predictable compiles.** *Productivity is proportional to iteration
  speed.* Macro expansion and annotation processing are a major cost in clean
  compile time; avoiding them keeps the edit–run–see loop short.
- **Tooling can follow the code.** *The IDE is a first-class reader.* Custom
  macros are notoriously hard for IDEs to see through — go-to-definition,
  completion, and error spans all degrade. Tel prefers features an IDE can
  follow.
- **Readability.** Code that is generated by an arbitrary user macro is code a
  reviewer cannot read at face value. *If it looks correct, it probably is
  correct* fails when what you see is not what runs.

So Tel rejects the heavyweight options outright (see
[antifeatures](../02-philosophy/04-antifeatures.md)):

- **No Rust-style procedural macros.** A proc-macro takes near-arbitrary token
  input and emits arbitrary Tel — unbounded, opaque to tooling, slow to
  compile. The Rust ecosystem ships *five* flavours (declarative,
  declarative-2.0, derive, attribute, bang); that proliferation is exactly
  the thing to avoid. Writing macros is something Tel wants to avoid; it keeps
  the count at zero.
- **No runtime macro / `eval`.** See [Reflection](02-reflection.md).
- **No `build.rs`-style pre-compile scripts**, no operator/precedence
  customisation, no template metaprogramming, no C-preprocessor-style text
  substitution.
- **No author-defined annotation processors.** A Java-style `@Annotation`
  hooked to a user code generator runs into the same tooling and stability
  problems as proc-macros, plus a notorious compile-ordering hazard: if class
  A's `@Immutable` generates code that class B depends on, the compiler must
  know to compile A first — and the answer in practice ranges from "fragile"
  to "a separate build phase." Tel sidesteps the whole question by not having
  user annotation processors at all. The fixed-set [`derive`](03-derive-and-attributes.md)
  attribute is the one narrow exception.

### The "macros enable IDE refactoring" argument, inverted

There is a claim that Java was *uniquely positioned* to benefit from automated
refactoring because it deliberately omitted a macro system.
Tel takes the same bet: an IDE that can see every call site and every
definition without first running a user-defined expander is an IDE that can
rename, inline, extract, and migrate with confidence. Every macro Tel adds
is a slice of that confidence given back.

## What Tel allows: no macros at all

Tel has **no macros** — not author-written, and none in the standard library
either. There is no macro facility for a script or a library to reach for, not
even the narrow "leaf-code" shape described below.

What other languages ship as macros — `println`/string-formatting, `vec!`-style
collection literals, `assert`, `derive` — Tel provides as **compiler
builtins**. Because the compiler implements them directly, they are *by
definition not macros*: there is no macro language, no user-visible expansion
phase, and nothing for the IDE to see through. They behave like primitive
syntax or ordinary functions, and the standard library is a *consumer* of these
builtins, not a place that defines macros of its own. "Build it into the
language" below means exactly this — a compiler builtin, not a stdlib macro.

The remaining metaprogramming use cases are split across the alternatives that
follow:

- **[Alternative 1](#alternative-1-build-popular-macros-into-the-language):**
  whatever would be a popular macro is built into the language as a real
  construct (printing, builders, `derive`-style equality/hashing).
- **[Alternative 1b](#alternative-1b-script-authored-codegen-via-stdtel_ast):**
  everything domain-specific is ordinary Tel code that builds an AST and writes
  a `.tel` file the next compile picks up, via
  [`std.tel_ast`](../17-standard-library/18-tel-as-data.md). This is *not* a
  macro — no expansion phase, no call-site magic, no new IDE story to teach.

Between them these cover what almost every script wants. The reasoning is the
same iteration-speed and tooling argument as above, applied to the *cheapest
possible* macro: even a self-contained leaf-code macro adds an expansion phase
the IDE must learn to see through, a caching-and-reproducibility surface every
host must reproduce identically, and a "where did this code come from?"
question for reviewers. Leaf-code macros are "pretty easy," but *any*
script-authored macro hurts tooling, and the language should stay "somewhat
limited … without macros." That lean wins for Tel1.

The cleanest in-language alternative to a leaf-code macro is therefore *not* a
new macro feature at all but ordinary codegen: write a normal Tel script that
builds an AST and writes a `.tel` file the next compile picks up. That keeps
the generator inside the ordinary language and the ordinary type system, with
no new expansion phase to teach the IDE. See
[Alternative 1b](#alternative-1b-script-authored-codegen-via-stdtel_ast).

The rest of this section is **parked**: it records what the one narrow macro
shape Tel keeps reconsidering would look like, and the bar it would have to
clear, so a future "let's add macros" proposal does not start from scratch.
None of it is part of Tel1.

<summary><strong>Parked — the leaf-code macro shape and its requirements (kept only for a hypothetical future reconsideration; not part of Tel1)</strong></summary>

There is one narrow macro shape that is cheap enough to keep reconsidering: a
macro that produces **leaf code**.

> **Leaf code** is code that cannot refer to existing types or names from the
> surrounding program. A leaf-code macro is just *text turned into standalone
> code*, expanded as the first step of compilation.

Because the output is self-contained, a leaf-code macro is easy to reason
about: it cannot reach into the program's types, cannot capture surrounding
bindings, and the result is ordinary Tel that the compiler and the IDE see
normally. It is closer to a templated code generator than to a Rust macro.

This is strictly weaker than a proc-macro — it cannot, for example, derive a
trait implementation against a user's type, because that *requires* referring
to an existing type. Those use cases are handled by the alternatives above.

### Shape of a hypothetical leaf-code macro

If Tel ever ships this, it should look roughly like:

```tel
# Illustrative — not a settled syntax.
macro perfect_hash(keys: List[Text]) -> tel.Module {
    # ...compile-time code that returns a parsed Tel AST...
}

# At use:
const LOOKUP = perfect_hash!(["alpha", "beta", "gamma"])
```

Notes baked into this design:

- **The macro language is Tel itself.** A separate template DSL is a mistake;
  reusing the host language is what Zig and Terra do well. "I probably need an
  interpreter for it — if it's just Tel, the existing interpreter serves
  another purpose beyond experimental playground."
- **AST in, AST out — never strings.** Token-level macros (C preprocessor,
  Rust `macro_rules!`) give up too much structure; the cost shows up as
  garbage error spans and IDE blindness.
- **Arguments are explicit and named.** A macro cannot see ambient bindings
  beyond its imports and its declared parameters. Macros should not depend on
  context, except imports; the rest must be passed as an argument. A macro that
  only works if you have a variable defined with a specific name is exactly the
  failure mode to avoid. This is the leaf-code constraint, restated.
- **No partial declarations.** A macro emits whole top-level items, never a
  fragment (a single field of a struct, half an expression). Rust's
  `macro_rules!` cannot emit one struct field at a time, which is a real pain
  point; Tel's leaf-code form makes it a non-issue by construction.

### Hard requirements if Tel ever ships any macro facility

Any Tel macro feature would have to satisfy a fixed checklist. Recording it
here so a future "let's add macros" proposal has a bar to clear:

- **Error spans point at user source**, not into generated code. Generated
  code is inspectable as a secondary view, but the *primary* error location is
  the call site the author wrote.
- **Generated source is easy to dump and read** — comparable to C's "run the
  preprocessor and look." This single property prevents most "where did this
  come from?" debugging dead-ends.
- **Macros are fast to compile** and **their results are cached**. A clean
  compile that re-runs every macro every time defeats the iteration-speed
  maxim.
- **Reproducible** for normal use — same inputs, same output. A macro that
  reads the clock or RNG is a build-reproducibility bug.
- **Predictable I/O footprint.** Any file the macro reads (fixtures, schema
  files) must be registered with the compiler so incremental rebuilds know
  to re-run when it changes. The same goes for directory scans and
  attempted-reads of missing files — newly-appeared files have to invalidate
  the previous result.
- **Predictable name footprint.** It must be cheap for the compiler to know
  which top-level names a given macro invocation introduces or modifies,
  without re-expanding every macro in the unit. Otherwise importing one name
  from a module forces expanding every macro it contains.
- **Sandboxed execution.** Macros (and any build-time code) run inside a WASM
  sandbox so a malicious dependency cannot read the
  developer's filesystem at compile time. This matches Tel's
  capability-based runtime model.
- **Macro-only dependencies are scoped separately** and do not ship in the
  resulting artifact.
- **Cross-crate use is by explicit name only.** A macro defined in crate
  A is usable from crate B if B imports it by name — no glob exposure, no
  implicit re-exports.

Most of these requirements are not free; together they are a lot of
machinery. That cost is itself an argument for *not* adding the feature.

#### Same-crate use, ordering, and bidirectional generation

A separate cluster of expectations governs how macros interact with the rest
of the program *in the same compile unit*:

- **Macro code lives next to the code that uses it.** A macro is allowed in
  the same crate as its callers; pushing macro definitions into a separate
  side-crate is a deliberate non-goal.
- **Hand-written and generated code see each other.** Normal code can call
  generated code; generated code can call normal code; generated code can call
  other generated code. (The last is allowed but needs ordering rules — see
  below.)
- **Incremental result equals clean result.** A macro that produces different
  output between an incremental rebuild and a clean rebuild is a bug.
  Combined with the "predictable name footprint" requirement above, this is
  what lets the compiler skip re-expansion when nothing relevant changed.
- **Macros must work in their own compile module**, not only across module
  boundaries. The Rust pattern where a macro in module M cannot see consts
  also defined in M when invoked from elsewhere is cited as a thing to avoid.

The hard part is ordering. If macro `A` generates a type that macro `B` then
references, the compiler has to expand `A` first. The Java annotation-processor
ecosystem solved this with a separate, fragile pre-compile pass; Tel's leaf-code
restriction sidesteps most of the question (a leaf-code macro cannot see another
macro's output by name in the surrounding scope), but **does not** answer it for
the "build popular macros into the language" path where, e.g., a derived
implementation references a generated supporting type.

#### Pre-publish expansion, type-checked macros

Two more ideas worth recording as bars for any future macro proposal:

- **Pre-publish expansion.** When a crate is published as *source*, expand
  internal (non-public) macros once at publish time so downstream consumers
  don't re-run them — and apply the same logic to monomorphising generics
  over private types. Faster downstream builds, but the published source no
  longer matches what the author wrote. Moot if Tel ships no author-written
  macros.
- **Type-checked-at-declaration macros.** Could a macro language be designed
  so every error is caught at the declaration site, with no new errors no
  matter what arguments are passed? If yes, IDEs can rename and complete
  across macro boundaries. If no, the macro language is effectively
  dynamically typed. The catch: a language strong enough to satisfy this is
  roughly *parametric generics with trait bounds* — which Tel already has, so
  if the type-checkable subset of "macros" is just generics, do not call it
  macros.

[`std.tel_ast`](../17-standard-library/18-tel-as-data.md) instead.

Decided for Tel1: **no script-authored macros**, not even the leaf-code form.
The alternatives below cover the real cases; revisit only if a concrete need
appears that none of them can serve.

## Alternative 1: build popular macros into the language

The strongest direction here: **whatever would be a popular macro, build it
into the language instead** — if it is not too complex. "Build it into the
language" means a **compiler builtin**: the compiler handles it directly, so it
is not a macro at all (see [above](#what-tel-allows-no-macros-at-all)).

Examples:

- `println` / string-formatting helpers — a compiler builtin, not a macro.
- Builder generation and `Immutables`-style boilerplate — a compiler builtin.
- `derive`-style equality, hashing, debug-printing — see
  [Derive and Attributes](03-derive-and-attributes.md).
- **Context-aware logging** (a primary motivating case). The example is a block
  that automatically adds context for the duration of its body:

  ```tel
  # The desired shape — make this look like an if/else without
  # needing a macro for every "do something around a block."
  if FeatureToggle.USE_NEW_THING {
      log.with_context(USE_NEW_THING) {
          # body runs with the context set
      }
  } else {
      log.with_context(not USE_NEW_THING) {
          # body
      }
  }
  ```

  The right answer in Tel is **not** a macro: it is a normal function that
  takes a closure, plus enough closure ergonomics that calling it reads like a
  built-in control structure (trailing-closure syntax, non-local
  `return`/`break`/`continue` from the closure into the enclosing function,
  and inherited receivers where they make sense). The user-visible feature
  Tel needs is *good closures*, not *macros that look like closures*.
  TODO(open): closure ergonomics needed to make this work belong in the
  syntax chapter — confirm the syntax chapter actually covers
  trailing-closure form and non-local control flow, and link from here once
  it does.
- `autoclosure` / `lazy` — converting `f(some_expression)` into
  `f(|| some_expression)` automatically, with the result cached after first
  evaluation. This is a candidate language feature, not a macro.
  TODO(open): lean is "probably not" — it is an implicit conversion, and
  Tel rejects implicit conversions (see
  [antifeatures](../02-philosophy/04-antifeatures.md)). The need (cheap
  lazy parameters) may be better served by ordinary closure values, written
  explicitly at the call site. Decide and document.
- Serialisation (`serde`-style) — not a macro and not built in; data models
  are **schema-first**, with data classes produced as a separate generated
  module. The Serde-in-Rust experience is cited as a cautionary tale:
  derive-macros run before type information is available, so Serde cannot
  generate a JSON schema from the same declaration that drives
  serialisation. Tel's split (schema-first, codegen as a separate step)
  avoids the timing problem.
- **Zig-style `comptime`/inline loops** — running ordinary code at compile
  time and unrolling loops with known bounds. The idea is appealing but Tel
  leans toward not exposing a special keyword; see
  [Compile-Time Evaluation](04-compile-time-evaluation.md).
- **Zig-style generics-as-functions-returning-types** — appealing but
  rejected: it leans on heavy compile-time evaluation and a dependently-typed
  flavour that conflicts with predictable AOT compiles. Tel sticks with
  ordinary parametric generics. TODO(open): there is real interest in this;
  record the rejection and the alternative (richer trait bounds)
  explicitly if anyone re-asks.

The trade-off is explicit: a built-in is fixed forever (it cannot be revised
once Tel is frozen), so only constructs that are *clearly* right earn inclusion.
A built-in that 90% of users would want as a macro is worth freezing; a
speculative one is not.

TODO(open): this strategy is in tension with the stability priority — every
built-in is permanent (the language should be frozen once good). The
resolution is conservatism: only long-proven,
universally-wanted constructs (printing, basic derives) go in; everything else

## Alternative 1b: script-authored codegen via `std.tel_ast`

The "build popular macros into the language" path covers what almost every
script wants. Anything left over — domain-specific generators (ORMs, route
tables, mappers between data shapes, derived/cached properties, schema
migrations) — is served by ordinary Tel code that builds an AST and writes a
`.tel` file the next compile picks up. See
[`std.tel_ast`](../17-standard-library/18-tel-as-data.md).

This is *not* a macro: there is no expansion phase, no call-site magic, no
new IDE story to learn. The generator is a normal script the user can run, the
output is a normal file the user can read, and the next `tel build` consumes
both. The host's build chain controls when generators run.

Tel concentrates the metaprogramming use cases onto this single mechanism on
purpose:

- One reviewable artifact per generator (the generator) and one for its
  output (the generated module on disk).
- No "where did this code come from" mystery — it came from the file the
  generator wrote, which a human can open.
- No host-implementation cost beyond evaluating Tel and reading/writing files.

## Alternative 2: host-injected AST transformations

Rather than letting *scripts* author macros, the **host** could supply AST
transformations that run over a script before compilation.

This keeps the power out of untrusted script authors' hands and puts it with
the host, which is already the trusted party in Tel's model. It also means
"frontend" behaviour is a host/tooling concern, not a language feature each
implementation must reproduce.

Design constraints, if adopted:

- Transforms operate **AST-to-AST**, never on token streams or strings. The
  OCaml PPX experience is cited as a warning: AST node shapes change when
  language features are added, and PPX needs migration infrastructure to keep
  third-party transforms working across versions. Tel mitigates this two
  ways — the language is frozen (so the AST is too) and any host transform
  must produce *valid standalone Tel*.
- The transformed program must be **valid Tel on every other host**. A host
  is allowed to *add* a transform that simplifies how scripts in *its* world
  are written, but the result must still parse and compile under a different
  host that does not run that transform — otherwise the
  one-script-many-hosts guarantee is broken.
- The transform must be **visible to tooling**. The IDE shows both the
  before and the after; jumping to a definition lands on real source, not on
  generated code.

## Alternative 3: structured AST-matching transforms

A more constrained idea: a way to describe transformations as **structured
AST patterns** — match a tree shape, rewrite it — rather than free-form token
macros. This is the same machinery behind the
[IDE suggestion patterns](03-derive-and-attributes.md#ide-suggestion-patterns)
(e.g. suggesting `filter` → `keep`). The key observation: this works for
*annotation-style* macros where the input is already valid Tel, but not for
Rust-style macros where the input is near-arbitrary.

## Explicitly rejected metaprogramming asks

Several ideas look attractive at first glance. Each is rejected here so the
next reader does not have to re-derive the reasoning.

- **Macros that vary by argument type.** Could a macro inspect the static
  types of its arguments and emit different code per type
  (the Rust `derive` timing complaint, restated). The answer is no: anything
  that needs to dispatch on a type *is* generics with trait bounds, plus
  possibly compile-time evaluation. If a real use case slips through, prefer
  generalising generics over adding a typed-macro layer.
- **Macros that emit unnameable types** (state machines synthesised from
  transition lambdas, etc.). The closure-like "anonymous type returned by a
  factory" pattern is fine as a *language* feature (a function returning an
  opaque type), but it should not require a macro to make. TODO(open): the
  exact story for opaque return types lives in the types chapter; link once
  written.
- **Macros that change a binding's type partway through a function** (the
  `UserBasic + free UserAuth?` sketch — return type assembled from
  what the function did along the way). Tel rejects this: a binding has one
  type, full stop. The use case (parts of a value loaded on demand) is
  handled by composing optional fields in an ordinary record, not by mutating
  the *type*.
- **Static URL/route trees with compile-time validation.** Consider a
  long sketch of building a routing tree where
  `home.user.profile.url()` is a static error if the path does not exist.
  This is a *narrow* use case that demands either compile-time evaluation of
  a tree built at startup, dependently-typed members, or a custom macro
  language — all of which lose more than they win. Tel's answer: use ordinary
  data and statically-typed identifiers; let the host catch missing routes
  with a startup-time check. TODO(open): if a future Tel use case really does
  need a tree of named referable static fields with iteration, revisit.
- **Statement-level monomorphisation hints.** ("If `targets` is empty,
  monomorphise this branch with `LayerQueue`.") See
  [Compile-Time Evaluation](04-compile-time-evaluation.md#not-in-scope-pgo-and-optimisation-hints).
- **Efficient predicate-driven generators** like `i % 3 == 0 and 0 <= i < 100`
  compiled into tight stride code. Lovely if free; not worth a macro. The
  idiomatic Tel answer is `range(0, 100).filter(|i| i % 3 == 0)` and trust
  the compiler/host to fuse what it can.
- **Custom DSLs via macro-defined control flow.** Tel deliberately keeps the
  set of control-flow constructs fixed. The need is real (see the
  context-logging example above); the answer is closures plus
  trailing-closure call syntax, not a macro system that lets every library
  invent its own `if`-shaped thing.
