## Core (always on)

- **Strict static typing.** Programs do not run with type errors. Inference is allowed where unambiguous, but public signatures require explicit types.
- **Expression orientation.** Most constructs (blocks, `if`, `match`, loops where sensible) are expressions that produce values. Small scripts stay small.
- **Stable surface.** Backwards-compatible by default. A Tel script from today should still run unchanged years from now. Breaking changes are the last resort, not the default.
- **Capability-based I/O.** Any I/O — files, network, time, env vars, randomness, anything outside the program — is delivered as an explicit *capability* the host passes in. Code that wasn't given a capability cannot use it. This makes every Tel script effectively sandboxed; it also makes time, randomness, and external state trivially mockable for tests. Hosts may legitimately offer fewer capabilities (a browser host has no filesystem), and scripts must cope.
- **Determinism by default.** Given the same inputs and the same injected capabilities, a Tel program produces the same outputs — bit-for-bit, on every host. Anything non-deterministic (current time, randomness, ambient state) is *only* reachable through an injected capability, so the script cannot acquire it by accident. This is what makes cross-host reproducibility, audit trails, and replay debugging tractable. - **Optimisation-friendly by construction.** Tel makes no promise about *how fast* a host runs a script — that is the host's call. But the language is designed so that an optimising backend *can* produce fast code: no `eval`, no reflection, no dynamic class loading, no escape hatches that block whole-program analysis. The script cannot reach for raw threads, hand-tuned memory layout, or SIMD intrinsics either — performance comes from a good backend on the right host, not from low-level knobs in the source. A feature that would force a backend to give up optimisation (or that would let a script "just do fast stuff" by skipping the type story) does not earn its place. - **Host-portable concurrency.** A program can ask to *spawn a task*, but Tel makes **no promise** about whether tasks run in parallel, on a thread pool, on fibers, on an async runtime, or sequentially on a host tick. This lets the same script run inside hosts with very different concurrency models. The user-visible abstraction is *tasks*, not threads, and tasks should compose (combine, race, await, cancel) cleanly. TODO(open): the concrete API for spawning, joining, cancelling, and propagating errors needs more thought — see chapter 14.
- **Traits / interfaces with polymorphism.** Behaviour is described by traits (final naming TBD), and types implement them. Polymorphism is via trait dispatch. There is **no class inheritance**.
- **Untagged union types and exhaustive matching.** "One of N possibilities" is an *untagged union* — `(A | B | C)`, written by listing the member types. There is no separate tag or constructor: a value's *type* is its tag, and `match` dispatches on that type. Unions flatten and deduplicate — if `X = (A | B | C)` and `Y = (C | D)` then `(X | Y)` is exactly `(A | B | C | D)`, with the two `C`s being the same `C`. Exhaustive `match` over the members is a first-class control-flow construct. A union may opt in to being *non-exhaustive*, letting libraries add members without breaking downstream `match`es.
- **Result-style error handling.** Errors are values, returned through a `Result`-shaped type, propagated explicitly. There are no exceptions and no surprise control flow.
- **Refined / newtype-friendly types.** Wrapping primitives in meaningful types (`Id[Person]`, `EuroAmt`, `NonEmpty[List[T]]`) is cheap and encouraged. Anything the built-in types can do, user-defined wrappers should be able to do too — the one exception being the stdlib-only concurrency capability `Sync` (interior mutability shared across tasks), which is sealed in the standard library for data-race safety (see [`../14-concurrency-and-parallelism/07-memory-model-for-concurrency.md`](../14-concurrency-and-parallelism/07-memory-model-for-concurrency.md)).
- **Design-by-contract.** Pre-conditions and post-conditions on functions ([`requires`/`ensures`](../09-functions/01-function-declaration.md#pre-and-post-conditions)) and type-level invariants are first-class. They are compile-checked when the compiler can prove them and runtime-checked otherwise. Asserts, contracts, and refined types are part of the *type story*, not bolt-on annotations. Invariants that need *judgement* rather than proof (*"transfer always checks authorisation first"*) are stated as prose [review invariants](../18-tooling/07-linter.md#review-invariants--unprovable-re-checked-on-change) that review tooling re-checks when the code changes — the unprovable tier of the same spectrum. ## Opt-in (project-scale)

These features exist so Tel can scale beyond a single script, but they do not get in the way when you only want a 30-line embedded hook:

- **Modules** with explicit imports. The importing side may alias an import as a whole — `import b.c as a` — which doubles as the way to resolve a name conflict between modules. It may not rename or re-home a module's individual members: a member keeps the name it was defined with and stays under its own module, so member `m` of module `x` is never reached as `y.m`.
- **Visibility modifiers** (e.g. `pub` / private-by-default — exact spelling TBD). TODO(open): does `pub` even make sense for an embedded language where the host already chooses what to expose? Lean: yes, for *intra-script* encapsulation in larger Tel projects.
- **A package manager** for distributing reusable Tel code between Tel projects (not for distributing the host's resources).
- **Capability declarations per crate.** A dependency must declare which capabilities (network, filesystem, time…) it needs; the host can deny them. This is a supply-chain story: a malicious or compromised crate cannot acquire capabilities it didn't ask for.

A small script never has to mention any of these. They appear only when you reach for them.

## Tentative

- **Resource-bound execution mode.** A host can run untrusted Tel with caps on total ops or memory, so a runaway script cannot hang the host.
- **A "strict mode"** that promotes some opt-in project features (explicit modules, visibility on public items, no global mutable variables) to *required*. The idea: small scripts stay loose, larger projects opt into the stricter dialect. TODO(open): commit to or reject strict mode — the concern is that it splits Tel into two dialects.
- **Metaprogramming.** Embedded scripting normally favours *less* metaprogramming, not more — push back hard on inputs that assume otherwise. The minimum that pays its weight is probably: `derive`-style attributes (auto-generate equality, hashing, serialisation, debug-printing) and possibly compile-time evaluation of pure functions. Runtime reflection and Rust-style proc-macros are unlikely to fit. TODO(open): pick a minimal subset — or none — once real use cases demand it.
- **A generated public-API summary file** (signatures + inferred effects + declared contracts) committed alongside source, so diffs make public-API churn obvious. Useful for stability discipline; cost is one extra file to maintain. TODO(open): keep, drop, or punt to tooling.
