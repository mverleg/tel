# Antifeatures (and Why)

The features Tel deliberately *does not* have. Each entry pairs the omission with the priority it serves. See [`01-priorities.md`](01-priorities.md); the features Tel *does* have are in [`03-features.md`](03-features.md).

## Inheritance and dynamism

- **No inheritance.** Polymorphism comes from traits, not from extending a class. Inheritance leaks implementation across layers, complicates type checking, and pulls newcomers into class-first thinking — mixins and abstract classes are out for the same reasons. Traits and delegation give the same power without the trap. *Serves: one good way over many clever ones, readability over writability.*
- **No retroactive conformance or runtime trait registry.** A crate may not implement a foreign trait for a foreign type (the orphan rule); trait coherence is a static, crate-scoped guarantee with no process-global conformance table and no `as?`-style dynamic conformance test. This keeps one resolved impl per (trait, type) across a program — Swift's fully general retroactive conformance is the rejected alternative — and suits AOT and embedding. Extension is via a [newtype](../05-types/12-refined-types.md); the full rules are in [TIP-0005](../tips/0005-trait-coherence-and-the-orphan-rule.md). *Serves: safety over flexibility, stability over novelty, embedded scripts over standalone projects.*
- **No reflection, `eval`, or runtime type introspection.** No `eval`, no runtime type inspection beyond what trait dispatch needs, no dynamic class loading, no calling a function by a name built from a string. These defeat capability-based safety and obstruct AOT compilation. The alternative is a stronger static type system and schema-driven code generation. *Serves: embedded scripts over standalone projects, safety over flexibility, stability over novelty.*
- **No heavy metaprogramming.** No proc-macros, no runtime macro systems, no operator or precedence customisation, no template metaprogramming, no `build.rs`-style pre-compile scripts. Embedded scripting favours less metaprogramming, not more. Narrow exceptions such as `derive`-style attributes are listed in [`03-features.md`](03-features.md). *Serves: stability over novelty, one good way over many clever ones, readability over writability.*
- **No traits as values or union members.** A trait is a *bound* that constrains a type, never a type a value can have — there is no `let x: Drawable`. Dynamic dispatch goes through an explicit, separately-spelled trait-object form (`dyn Trait`), so static and dynamic dispatch never hide behind the same syntax. Union members are always concrete types (a trait object counts as concrete); a bare trait cannot be a member. This keeps union members provably disjoint, so every `match` arm is unambiguous, and there is no downcasting out of an open trait object. *Serves: one good way over many clever ones, readability over writability, safety over flexibility.* See [`../10-data-modelling/02-union-types.md`](../10-data-modelling/02-union-types.md) and [`../10-data-modelling/03-traits-or-interfaces.md`](../10-data-modelling/03-traits-or-interfaces.md).
- **No dependency-injection framework or implicit wiring.** Tel has no DI container, no autowiring, no annotation- or classpath-scanning, and no macro- or reflection-built object graph (the Dagger / Spring `@Autowired` / Guice `@Inject` model). Dependencies are passed as **ordinary explicit parameters** — the same capability-passing that hands a script its `Clock` and `Log` from the host (see [The host boundary](#the-host-boundary) below). The "wiring" of a program is therefore plain constructor code a reader and an IDE can follow to its source, not a graph a framework synthesises at build or startup time from annotations. The same reasoning rejects every *"scan for annotated members and wire them up"* framework — annotation-driven HTTP **routing** (`@GetMapping`/`#[get]`), service auto-registration (`ServiceLoader`/`@AutoService`), and aspect/AOP advice (`@Transactional` weaving): registration is **explicit** (a value you construct and hand to a router/registry), wrapping behaviour is an ordinary [trailing-closure](03-features.md) call, and anything genuinely data-driven is a visible [codegen](../15-metaprogramming/01-macros.md#alternative-1b-script-authored-codegen-via-stdtel_ast) step, never hidden expansion. A web framework or router is a *library*, never part of the language (see the bundled-tooling open question below). *Serves: readability over writability, one good way over many clever ones, embedded scripts over standalone projects.* Builds on [no reflection](#inheritance-and-dynamism), [no heavy metaprogramming](#inheritance-and-dynamism), and [capability-based I/O](03-features.md).
- **No implicit or contextual parameter passing.** A cross-cutting value — a logger, a config, a tracing scope, bundled as a `Context` — is **declared in the signature and passed explicitly at every call site**, like any other argument; the compiler never forwards an argument the author did not write. The *implicit-passing* alternative (declare it everywhere, but let the compiler thread it for you at call sites — Scala's `using`/`given`, Kotlin's context parameters and the deprecated context receivers, Haskell's implicit parameters) was explored and rejected. It reintroduces the one piece of action-at-a-distance that [no global mutable state](../06-bindings-and-scope/07-no-global-mutable-state.md) exists to remove — what a call hands its callee stops being visible at the call — and every language that shipped it reports the *resolution rules* (which value is in scope, ambiguity when two are, shadowing, import-driven "magic") as a headline regret: Scala 3 split the overloaded `implicit` into `given`/`using` and demoted implicit conversions, and Kotlin deprecated context receivers in favour of *named* context parameters precisely because the implicit-receiver form was un-toolable. Explicit passing costs boilerplate; that cost is paid down by **bundling** many capabilities into one `Context` value (the Go `context.Context` pattern), and the visibility it buys is the point. *Serves: readability over writability, one good way over many clever ones, safety over flexibility.* Builds on [no DI framework or implicit wiring](#inheritance-and-dynamism) — the same "dependencies are ordinary explicit parameters" rule applied to cross-cutting values.

## The host boundary

- **No ambient I/O or OS access.** A script cannot touch files, the network, the clock, environment variables, randomness, or any other OS facility unless the host hands it a capability for that operation — no global `stdout`, no implicit filesystem, no ambient clock, no global RNG. The same script then runs in a browser, a desktop app, a backend, or a game engine, and copes when a host offers fewer capabilities. *Serves: embedded scripts over standalone projects, safety over flexibility, reproducibility.* `TODO(open): one proposed exception — ambient `print`/`eprint` for diagnostics, since requiring a threaded capability just to drop in a debug print is painful and a console almost always exists. Structured output stays capability-gated. Decide here, as it bends this maxim — see [`../17-standard-library/10-os-and-process.md`](../17-standard-library/10-os-and-process.md).`
- **No low-level machine access.** User code never sees threads, mutexes, atomics, memory barriers, raw addresses, pointers, alignment, endianness, or interrupts, and there are no SIMD or GPU intrinsics, PGO hints, or `unsafe` escape hatch. The host owns the machine; a program reasons about values and types, never the bytes underneath. Tel does not compete with C — where speed trades against stability or portability, speed loses; a host that needs native work exposes a capability for it. *Serves: embedded scripts over standalone projects, high abstraction over low-level control, stability over novelty.*
- **No first-class async or function colouring.** Tel does not bake an async/await runtime into the language and does not split functions into "async" and "sync" colours. Concurrency is expressed through *tasks*; the host decides what running a task means — a fiber, a worker thread, a JS microtask, a sequential continuation. Code still works on a host with no concurrency at all. *Serves: embedded scripts over standalone projects, host-portable concurrency.*
- **No `Future` or `Promise` type.** There is no constructible future/promise value you build, pass around, and await separately from a task. A [task handle](../14-concurrency-and-parallelism/02-tasks.md) *is* the future and `join` is the await — one awaitable, not two. The narrow "resolve later" and "many readers of one result" needs are served by a settable `Sync` cell (`Once[T]`), a sharing primitive rather than an awaitable type. A free-standing future adds a second awaitable concept and tends to drag function colouring back in. *Serves: one good way over many clever ones, embedded scripts over standalone projects.* See [no `Future` or `Promise` type](../14-concurrency-and-parallelism/03-async-and-function-colouring.md#no-future-or-promise-type--the-task-handle-is-the-only-awaitable).
- **No microcontroller-style constraints.** Tel is for host-application embedding, not resource-starved hardware. Memory layouts, allocation, and runtime features assume a normal host on normal hardware. A proposal optimising for `no_std`-style constraints is aimed at the wrong language. *Serves: embedded scripts over standalone projects, one good way over many clever ones.*
- **No required shared heap.** Every language feature and `std` API is specified so a host with strictly isolated per-task heaps can implement it. The one bounded exception is `std`'s platform-conditional shared-mutable primitives (`ConcurrentMap`, cloneable channel senders, mailboxes — see [`../17-standard-library/12-concurrency-utilities.md`](../17-standard-library/12-concurrency-utilities.md#shared-mutable-types-platform-conditional)); hosts that cannot provide a shared region may omit them. Any other proposal that depends on heap sharing for correctness is flagged. *Serves: embedded scripts over standalone projects, host-portable concurrency.* See [`../14-concurrency-and-parallelism/07-memory-model-for-concurrency.md`](../14-concurrency-and-parallelism/07-memory-model-for-concurrency.md#shared-heap-is-never-required).

## Surface and semantics

- **No exceptions or *recovering* unwinding.** Errors are values, returned through `Result`-shaped types and propagated explicitly — no throw/catch, no exception object travelling upward, no surprise control flow. Truly unexpected conditions abort the task; recovery happens at a defined boundary, not in the middle of the work. (Abort *does* run a **NoPanic, non-recovering** cleanup unwind that settles live linear resources and any `finally` blocks on the way down — a `finally` may release a resource but can never catch the abort or resume past it; see [panics and aborts](../13-error-handling/04-panics-and-aborts.md#abort-never-catch).) *Serves: readability over writability, safety over flexibility, one good way over many clever ones.*
- **No implicit conversions or DWIM.** No implicit numeric widening, no truthy/falsy coercion, no automatic string ↔ number, no silent NaN propagation, no quiet integer overflow. Anything that could be a problem becomes a clear problem at the source — the programmer writes the conversion. *Serves: readability over writability, safety over flexibility.*
- **No `null`, setters, or uninitialised variables.** Every binding is initialised where it comes into scope. There is no `null` — optionality is an `Option`-shaped type — and no implicit setters; mutation, where it exists at all, is explicit and marked — a `let uniq` binding or a `!T` mutable type (the [mutability model](#open-questions) is decided in [TIP-0001](../tips/0001-mutability-and-borrowing.md)). *Serves: safety over flexibility, readability over writability.*
- **No space (juxtaposition) application.** A call is always written with parentheses — `f(a, b)`, never `f a b`. Letting a space mean application (so `min a b c` parses as `min(a, b, c)`) was considered for terse, DSL-style code but rejected: it forces a reader to hold two grammars at once, makes nesting ambiguous (`f x g y` is `f(x, g, y)`, not `f(x, g(y))`) so the convenience caps out at one shallow level, and the line-ending termination rule is a second, invisible piece of syntax. Parentheses are unambiguous and read the same everywhere. *Serves: readability over writability, one good way over many clever ones, familiarity over novel syntax.* See [`../07-expressions/06-function-application.md`](../07-expressions/06-function-application.md).
- **No custom operators or custom precedence.** Operators are a fixed, language-defined set with fixed precedence and associativity. There is no per-file precedence customisation, so code reads the same wherever you find it. Existing operators can still be *overloaded* for user types — see [`../04-syntax/04-precedence-and-associativity.md`](../04-syntax/04-precedence-and-associativity.md). *Serves: readability over writability, familiarity over novel syntax.*
- **No universal receiver (bare-name fall-through on every first argument).** Method syntax already unifies *calls* — `x.f(y)` is `f(x, y)` for any free function ([UFCS](../09-functions/08-method-syntax.md)) — so the first argument is the universal *call-site* subject. Extending that into the *body*, so bare names in **every** function resolve through the first parameter the way a method body reaches `self`, was considered for uniformity (a method and a [receiver closure](../09-functions/06-closures-and-lambdas.md#lambda-receivers) already share exactly that one rule) and rejected. Bare-name-through-`self` stays **opt-in**: either you are inside an `impl` — so `self` is a meaningful type — or the parameter carries a receiver type (`Recv.fn() : R`). Making it automatic for every first argument privileges an arbitrary parameter as a context even when it is not one (`add(a, b)`, `distance(p, q)`), forces a reader to know that argument's whole member set to know what any bare name means (the JavaScript `with`-statement regret, banned in strict mode for exactly this), and — with Tel's [collision-is-an-error](../09-functions/06-closures-and-lambdas.md#lambda-receivers) rule — turns every local that merely shares a field's name into a compile error in *every* function body. No mainstream language does this: the UFCS languages (D, Nim) stop at the call site, and the implicit-`self` languages (Kotlin, C++, Ruby, Scala) confine bare-name resolution to methods and declared receivers. The uniformity worth keeping — one notion of `self`, shared by methods and receiver closures — is preserved; only its *automatic* application to unmarked parameters is refused. *Serves: readability over writability, one good way over many clever ones, familiarity over novel syntax.* Related: [no implicit or contextual parameter passing](#inheritance-and-dynamism).
- **No raw pointers; lifetimes elided, `'a` only when needed.** Tel has high-level borrows written with Rust-style sigils — `&T` (a read-only borrow), `&!T` (an exclusive mutable borrow), and a rare, usually-elided `*` deref (see [`../12-memory-and-runtime/04-references-and-aliasing.md`](../12-memory-and-runtime/04-references-and-aliasing.md)) — but **`&` only ever means "borrow", never "address-of"**: there are no raw addresses and no pointer arithmetic. A borrow is a scoped value, not bytes. Borrow scopes are inferred and propagated structurally on the common path, so they are almost never written; when inference cannot resolve one (a return or stored field that could borrow from several sources), the fix is a **Rust-style `'a` lifetime parameter** (`&'a T`, declared in `['a]`) that ties the related inputs, returns, and fields to one scope. Tel follows Rust's `'a` spelling rather than inventing its own — the same familiarity argument as the `&` sigils. What Tel refuses is not the `'a` spelling but raw pointers and any *obligation* to write a lifetime where elision succeeds; the difference from Rust is frequency, not syntax. Following the one mainstream borrow language (Rust) is deliberate — it reuses the `&`-means-borrow intuition a large audience already has, while the no-raw-pointers guarantee refuses the C address-of reading `&` carries elsewhere (which is exactly the [Swift `inout`-`&` confusion](https://belkadan.com/blog/2021/12/Swift-Regret-inout-Syntax/), avoided here because `&` never means two things). *Serves: readability over writability, high abstraction over low-level control, familiarity over novel syntax.* See [TIP-0001](../tips/0001-mutability-and-borrowing.md).
- **No iterator give-back sugar (the "resuming borrow").** A *linear* iterator — one that cannot be polled after it ends — is written as a plain consuming `next(self) -> More(T, Self) | Done`, threading the tail through the return; `for` hides the re-thread for users and combinators encapsulate it. A proposed sugar that spelled this as a `&!self` borrow whose give-back is conditional on the return variant (plus a `consume` keyword) was rejected: it overloads `&!` with two opposite ownership meanings behind one sigil, removes a tax (`it = rest`) that only hand-written resource loops ever pay, and needs flow-sensitive revival of the caller's binding — implementation surface the explicit form avoids. *Serves: one good way over many clever ones, readability over writability.* See [TIP-0011](../tips/0011-resuming-borrows-and-linear-iterators.md).
- **No identity-revealing operations on values.** `==` on values is *structural*; there is no reference-equality operator (`is` / `===`), no address or pointer access, no identity-keyed hash, no reflection that distinguishes "clone of X" from "reference to X." Identity is unobservable, which is what lets the runtime serve "shared immutable" data either by pointing many tasks at one allocation or by copying per task, indistinguishably (see [`../14-concurrency-and-parallelism/07-memory-model-for-concurrency.md`](../14-concurrency-and-parallelism/07-memory-model-for-concurrency.md#identity-is-not-observable-on-values)). *Serves: embedded scripts over standalone projects, safety over flexibility.*
- **No weak references (user-visible).** Scripts and `std` expose no weak or soft reference type. A weak reference is an identity-revealing operation by another name — it would let a script observe whether a value is shared or copied, the very distinction the rule above hides — and it complicates the copy-at-task-boundary transfer and refcounting backends. Reclaiming a cycle inside a long-lived task is the *host's* GC strategy: a host may use weak references internally, but never surfaces one to Tel code. The narrow cases that reach for weakness elsewhere (non-retaining caches/observer lists, non-owning back-pointers in a user-built graph) are served by `Id`-indirection and stdlib `Sync` types instead. *Serves: safety over flexibility, embedded scripts over standalone projects, one script many hosts.* See [`../14-concurrency-and-parallelism/07-memory-model-for-concurrency.md`](../14-concurrency-and-parallelism/07-memory-model-for-concurrency.md).

## Conservatism

- **No runtime version churn or language editions.** New features arrive rarely and backwards-compatibly. There is no "Tel 2 incompatible with Tel 1" and no Rust-style editions; a decade-old script still runs, byte-for-byte the same. A change that must break compatibility ships as a *separate* language (Tel2), not a new version of Tel. Editions buy greater flexibility in language evolution, but the price is a version number stamped on every source unit — and for a small-script language that is a tax paid by the many to benefit the few migrations that justify it: a config snippet or a one-off automation script should not have to declare which dialect of the language it speaks. The price is worse than it looks because the annotation is often *unownable* in Tel's deployment story — when the runtime is supplied by a game engine, an apivolve evolution, or a config host, the script author does not choose the runtime and so cannot meaningfully choose an edition either. The evolution that editions promise is pursued instead through additive-only changes, long deprecation windows, and migration tooling, none of which need a per-file version marker. *Serves: stability over novelty, embedded scripts over standalone projects.*
- **No latest-and-greatest language tricks.** Tel may look conservative — even a bit old-fashioned — if that buys decades of stability. Features adopted because they are fashionable, rather than because they earn their weight in the priority list, are rejected. *Serves: one good way over many clever ones, stability over novelty.*

## Silent failure modes

These are not single features but recurring *patterns* the language design rejects, drawn from the catalogue of production bugs the design wants to prevent. Each is the same shape — *something went wrong, and the program kept going as if it hadn't* — and Tel pushes against all of them.

- **No silent default for missing data.** Deserializers, builders, and copy-update forms must not invent values for fields the input does not supply. A required field that is absent is an error; an optional field that is absent is an explicit `Option` value the reader has to handle. A repeated experience motivates the rule — Mongo patches that wiped data because the same Java class served input *and* output schemas, Avro builders that silently shipped without newly-required fields, deserializers that quietly skipped unknown fields — and this is the failure mode it rules out. See [`../10-data-modelling/01-records.md`](../10-data-modelling/01-records.md), [`../05-types/12-refined-types.md`](../05-types/12-refined-types.md).
- **No silently-dropped errors or unobserved task failures.** A `Result` cannot fall on the floor (see [`../13-error-handling/03-error-propagation.md`](../13-error-handling/03-error-propagation.md)); a spawned task whose failure nobody observes is a bug (see [`../14-concurrency-and-parallelism/04-structured-concurrency.md`](../14-concurrency-and-parallelism/04-structured-concurrency.md)); a thread-pool task that aborts without a handler is impossible because every pool ships with one (see [`../17-standard-library/12-concurrency-utilities.md`](../17-standard-library/12-concurrency-utilities.md)). The catalogue records dozens of "thread silently died" and "Result was ignored, the empty value was persisted" cases — all of this category disappears when a failure is structurally undroppable.
- **No data shared between tasks by accident.** [Per-task heap isolation](../14-concurrency-and-parallelism/07-memory-model-for-concurrency.md) means a value sent to another task is deep-copied; in-place mutation by one task cannot affect a value held by another. The recurring "simulation input was mutated by a later step, so the persisted input no longer matches what production saw" pattern is impossible by construction.
- **No string-typed flags or stringly-typed configuration.** A configurable behaviour is named by an enum-shaped union ([named-boolean enums](../10-data-modelling/02-union-types.md)) or by a typed value, never by a string the runtime parses. The catalogue cites a "true" → "true." typo that quietly returned `false` from `Boolean.parseBoolean` and disabled a feature in most environments; that bug class is structurally absent when a feature toggle is an enum the compiler checks.
- **No silent staleness.** A long-running background task that stops producing values should not look the same to readers as one that is still working. Channels distinguish *empty* from *closed* ([`../14-concurrency-and-parallelism/06-channels-and-message-passing.md`](../14-concurrency-and-parallelism/06-channels-and-message-passing.md)); the language pushes "no update for too long" into the type story rather than letting last-seen-value linger silently. The catalogue records repeated cases where stuck fitters produced stale GUI output, where a stopped background thread left 0.0 in a sparse grid that downstream code treated as real data, and where a missing schema-registry connection caused a publisher to silently drop everything.

## Naming and identity hazards

Several catalogue bugs stem from things being *named* in misleading ways. Tel cannot police naming taste, but several language-level choices push back:

- **Phantom-typed IDs** stop an `Id[User]` being passed where an `Id[Order]` is expected, even though both wrap the same integer (see [`../19-use-cases/09-entity-identity-and-projections.md`](../19-use-cases/09-entity-identity-and-projections.md)). The catalogue records bugs where one entity's key was looked up in another's map, and where an ID was inadvertently rendered as a user-facing string — both classes addressed by the phantom-ID discipline.
- **Refined units** (see [`../05-types/13-units.md`](../05-types/13-units.md)) prevent confusing `Duration`-shaped values whose actual units differ (nanoseconds vs milliseconds, packed dates vs timestamps, reporting currency vs trade currency). The catalogue cites several variants of this: a `toDate(Int)` that expected packed dates and a `toDate(long)` that expected timestamps; nanos-vs-millis mixups in cache lookups; greeks that differed only because of reporting currency.
- **Newtype wrappers for "different kind of the same scalar"** — `Celsius` vs `Fahrenheit`, `StrategyVol` vs `NaturalVol`, `RawValue` vs `DerivedValue` — turn a comment-only convention into a compile-time check. The catalogue records hours wasted on values that "looked the same" but were derived through different code paths.

## Open questions

- TODO(open): **Bundled tooling.** Whether Tel ships any application tooling *as part of the language* — and which. A web framework, ORM, or REST client clearly belong in libraries, not the language; a formatter or package manager plausibly belong with the language (a package manager is already listed in [`03-features.md`](03-features.md)). The host owns build, deployment, and process lifecycle. Decide the exact line.
- TODO(open): **Global mutable state.** Discouraged everywhere; possibly forbidden outright, at least in strict mode. Decide whether mutable globals are allowed at all, or only as immutable constants. Multiple inputs lean toward "not at all."
- **Mutability model — decided** (see [TIP-0001](../tips/0001-mutability-and-borrowing.md)). Tel has explicit unique bindings, spelled `let` / `let uniq`, plus type-level mutability via the `!T` sigil (`!Person` mutable, `Person` immutable). Copy-update (`with`) coexists; it is the non-mutating path. The earlier "immutable-values-only" direction is set aside.
- **Data-race safety** is achieved by making **mutable values affine**: a mutable value may be reached by at most one binding, so two tasks can never share a writable reference (see [`../12-memory-and-runtime/08-substructural-types.md`](../12-memory-and-runtime/08-substructural-types.md) and [TIP-0001](../tips/0001-mutability-and-borrowing.md)). This is mechanism (b) — mutability is a property of the *type*, spelled with the `!T` sigil (`!List` mutable vs `List` immutable) — combined with the affine rule, rather than (a) full Rust-style ownership of arbitrary values. The blessed stdlib shared-mutable primitives are the bounded exception (internally synchronised, `Sync`). TODO(open): promote to a maxim once the substructural topic is stable.
