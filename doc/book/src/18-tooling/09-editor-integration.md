## What

Editor integration is the **language-server surface** Tel exposes so that
editors and IDEs can give the user the same answers the compiler gives — type
information, completions, diagnostics, fix-its, go-to-definition,
find-references, rename, format, refactor, inline tests, inline benchmark
results, inspect-task-state on a paused debugger session.

There is one canonical implementation: the **Tel LSP server**, which is the
[compiler's friendly/incremental mode](01-compiler.md) wrapped in the
[Language Server Protocol](https://microsoft.github.io/language-server-protocol/).
Any editor that speaks LSP — VS Code, Neovim, IntelliJ, Emacs, Helix, browser
playgrounds — gets the full experience by pointing at the server.

## Why a single LSP is enough

The maxim **the IDE is a first-class reader — prefer features it can amplify,
reject features it can't follow** ([`../02-philosophy/02-maxims.md`](../02-philosophy/02-maxims.md))
is the load-bearing one here. Several design decisions in Tel only pay back
when there is an IDE to surface them:

- **Capability sets** are textual but the IDE can show them at the call site.
- **Refined types** ([`../05-types/12-refined-types.md`](../05-types/12-refined-types.md))
  are *the* tool that prevents a `ChickenId` from being passed to the
  `DrinkMachine` — but only if the editor flags the type-mismatch the moment
  the user types it.
- **Deprecation rewrites** from the [linter](07-linter.md) only stay friction-
  free if a one-keystroke fix-it is one keystroke away.
- **Trait dispatch** and **untagged unions** rely on the editor to show what
  a name actually resolves to, since the user does not always know which
  type a value has when reading a small script.

A single LSP keeps every editor on the same answers. The cost of
*not* shipping one is that each editor builds an inferior surrogate.

## What the server provides

A complete list — most of which are LSP-standard requests:

- **Diagnostics.** Type errors, lints, deprecations, formatter
  disagreements. Surfaced live, with the same wording the compiler uses on
  the command line. Errors continue past the first failure
  ([`01-compiler.md`](01-compiler.md)) so the editor's problems list is the
  full set, not the first one.
- **Hover.** Type, doc-comment, declared contracts, capability requirements
  for any symbol under the cursor.
- **Completions.** Context-sensitive identifiers and members, with the type
  shown inline. Completion items carry a `kind` (function, trait, refined
  type, capability, …) so the editor can icon them.
- **Go-to definition and find-references.** Across the project's module
  graph, including across the crate boundary into a dependency's source.
- **Rename.** Safe rename — no string-matching. Because Tel has no `eval`
  and no reflection, an identifier is reachable only through resolved
  references, and the rename is exact.
- **Quick fix-its.** Generated by the linter
  ([`07-linter.md`](07-linter.md)) and by the deprecation system in the
  standard library
  ([`../17-standard-library/01-stdlib-organisation.md`](../17-standard-library/01-stdlib-organisation.md)).
- **Format on save.** Calls the [formatter](06-formatter.md). Output is
  deterministic, so format-on-save never invalidates the user's cursor in a
  surprising way.
- **Run-test-at-cursor.** A `test fn` declaration gets a "run" code lens
  from the testing chapter ([`11-testing.md`](../14-testing/01-testing.md)). The result —
  pass, fail, skip — is shown inline.
- **Inline benchmark deltas.** From the benchmark history file the runner
  writes ([`11-testing.md`](../14-testing/01-testing.md)).
- **Inline capability annotations.** "This call needs `network`," "this
  call uses `filesystem(write = …)`" — the "asymptotic complexity
  at the call site" idea, but for capabilities.
- **Workspace symbol search.** Find any declared name in the project.
- **Live-error highlight for unobserved task failures.** Tied to the
  structured-concurrency design ([`../14-concurrency-and-parallelism/04-structured-concurrency.md`](../14-concurrency-and-parallelism/04-structured-concurrency.md)).

## What rides on the compiler

The LSP reuses the compiler's **friendly/incremental mode** for everything
above; it is not a separate program with its own type checker. The
[compiler chapter](01-compiler.md) is explicit: the LSP and the compiler
*share code*, and tracking is at the symbol level so editing one function
does not recompile its neighbours. Two implications:

- A diagnostic the editor shows is *exactly* a diagnostic the CLI compile
  would show. There is no "the IDE thinks the code is OK but `tel build`
  fails" failure mode.
- Adding a feature to the language is automatically reflected in the editor
  the moment the compiler supports it.

## Refactors

Beyond rename, the LSP exposes a small set of structural refactors:

- **Extract function / extract binding.** The selected expression becomes a
  function or `let`, with parameters threaded as needed.
- **Inline binding.** The inverse.
- **Move declaration** between modules, with imports rewritten.
- **Convert match arm to function**, **convert function to trait method**,
  and a few similar shape-preserving rewrites.

A refactor that would change observable behaviour is rejected by the server,
not offered as "potentially unsafe." The user does not get to ignore that
warning.

## Coupling-visible by design

A recurring principle: *isolate when possible, but if there is
coupling, make it explicit, clear, such that the IDE can find it, auto-
refactorable.* Tel leans into this:

- All cross-module references go through explicit
  [imports](../11-modules-and-packages/02-imports.md) — the IDE can build a
  precise edge graph.
- Capability use is declared at the crate boundary
  ([`../11-modules-and-packages/04-packages.md`](../11-modules-and-packages/04-packages.md)),
  so the IDE can paint a module green for "pure data" or amber for
  "filesystem" without running anything.
- There is no `eval` and no reflective dispatch, so a "find references" is
  exhaustive — there is no hidden caller.

Each of these is a small language commitment that compounds into a sharper
IDE surface. The precise edge graph is also rendered and diffed by a
dedicated util — and its per-change delta auto-attached to reviews — see
[Dependency Graph](../11-modules-and-packages/08-dependency-graph-and-locking.md#visualising-the-graph-and-its-diffs).

## Adjustable detail — show less, or show more

A reader rarely wants *all* of a declaration at once. The LSP exposes
**density levels** that fold a view of the code to the altitude the
reader is working at, then expand on demand. The same resolved model
that drives hover and go-to-definition drives this — there is no
separate outline parser.

The levels, from least to most detail:

- **Public API only.** Signatures of public declarations, with bodies,
  private items, contracts, and tests folded away — the *"what can I
  call"* view. This is the same projection the
  [documentation generator](10-documentation-generator.md) renders, so
  one model feeds both surfaces.
- **Business logic.** Bodies shown, but the *noise* folded: type
  annotations the compiler already infers, contracts, `test` blocks, and
  doc comments collapse to a marker the reader can expand. What is left
  reads as the algorithm.
- **Everything.** The full source — types, contracts, and tests inline.
  The default text view.

A reader switches level globally or per-declaration; folding is a view
concern, never an edit.

### Expand across boundaries

Detail also expands *outward*. Starting from a symbol, the reader pulls
in context in widening rings: a called function's signature, then its
body, then everything up to the **crate boundary** (stop at the edge
of the current crate) or the **stdlib boundary** (follow into
dependencies but stop at `std`).

Because every cross-module reference goes through an explicit
[import](../11-modules-and-packages/02-imports.md) and there is no
`eval` or reflective dispatch, the ring is *exact* — the editor knows
precisely which declarations an expansion reaches, with no hidden
caller. It is the same property that makes find-references exhaustive.

### Inline metadata

Alongside a declaration the server annotates counts and facts it already
computed: **"5 usages"** on a function, the capability set it needs,
whether a test covers it, its asymptotic complexity where declared.
These are code lenses over the resolved graph, not a re-scan of the
text.

These projections are not only for human readers. An AI assistant
working under a context budget can request *public API only* or
*business logic* to load the shape of a module without its full text,
then expand the rings it actually needs — the editor's folding model and
an assistant's context-trimming are the same operation.

## Notebook and playground front-ends

A browser-embedded LSP makes a playground viable — paste code, see types
and errors live. The same server, behind a different transport, could power an
LSP-aware notebook front-end. A notebook would build on an interactive
evaluation engine, which is currently a
[deferred feature](../20-appendix/06-deferred-features.md#repl) (the REPL): the
LSP/playground side stands on its own, but live cell *evaluation* waits on that.

## What editor integration does *not* do

- **No editor-specific lint rules.** All lints live in the linter
  ([`07-linter.md`](07-linter.md)); the IDE only *surfaces* them.
- **No surfacing of "code smells" beyond what the language and linter
  define.** The IDE is not an opinionated reviewer — it shows what the
  toolchain decided, not what an editor plugin thinks.
- **No formatting that differs from the formatter.** Format-on-save calls
  the same binary the CLI does.
- **No multi-language standard library presentation.** One idea was
  an editor that shows stdlib names in the user's natural
  language (English / Chinese). Punted: source is single-locale, see the
  [design history](../20-appendix/05-design-history-and-changelog.md).
